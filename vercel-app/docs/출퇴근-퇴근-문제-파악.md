# 출퇴근 퇴근 문제 파악 (분석만, 수정 전)

직원들이 보고한 현상과 코드 기준으로 **가능한 원인**만 정리했습니다. 수정은 하지 않았습니다.

---

## 1. 보고된 현상 요약

| 구분 | 내용 |
|------|------|
| **스토어** | สาขาเอกมัย (Ekkamai), Huamak, Silom |
| **증상 1 (Ekkamai)** | 퇴근(ออกงาน) 버튼을 누르면 **"บันทึกแล้ววันนี้"**(= 오늘 이미 기록됨)가 뜨는데, **실제로는 퇴근 시간이 저장되지 않은 것처럼 보임** |
| **증상 2 (Huamak, Silom)** | 퇴근(บันทึกออกงาน)을 누르면 **저장된 것처럼 되었다가 다시 이전 화면으로 돌아와서**, 퇴근이 완료되지 않는 느낌 |
| **공통 힌트** | 쉬는 시간(휴식), 끝나는 시간(퇴근 예정 시간)과 관련이 있을 수 있음 |

## 2. "บันทึกแล้ววันนี้"가 나오는 조건 (코드 기준)

- **메시지**: 태국어 `attDuplicateOnce` = "บันทึกแล้ววันนี้" (한국어: "오늘 이미 해당 기록이 있습니다.")
- **표시 조건**: API `POST /api/submitAttendance`가 **중복**으로 판단해  
  `success: false`, `message: "오늘 이미 [퇴근] 기록이 있습니다. 하루에 한 번만 기록할 수 있습니다."` 를 보낼 때, 클라이언트가 이걸 감지해 `attDuplicateOnce`로 알림을 띄움.

즉, **이 메시지가 뜨면 서버는 “이미 오늘 퇴근 기록이 있다”고 판단한 상태**입니다.

---

## 3. 서버 쪽 “퇴근 중복” 판단 로직 (`submitAttendance`)

- **대상**: `출근`, `퇴근`, `휴식시작`, `휴식종료` 는 **하루 1회만** 허용.
- **방식**:
  - `attendance_logs`에서  
    `store_name=ilike.{storeName}` & `name=ilike.{empName}`  
    로 최근 100건 조회 (날짜 조건 없음).
  - 각 row에 대해:
    - `log_at`을 **방콕(Asia/Bangkok)** 기준 날짜로 변환한 값이 **오늘(서버 기준 방콕 날짜)**와 같고
    - `log_type`이 요청한 타입(예: `퇴근`)과 같으면  
    → **중복**으로 간주하고, 위 메시지 반환 후 **DB에는 쓰지 않음**.

따라서:

- “บันทึกแล้ววันนี้”가 나왔다는 것은, **서버가 “이미 오늘 퇴근 로그가 있다”고 본 적이 있다**는 뜻입니다.
- 그런데 사용자는 “퇴근 시간이 안 들어갔다”고 느낄 수 있는 경우가 아래 4가지와 같습니다.

---

## 4. 가능한 원인 정리

### 4-1. 첫 번째 퇴근은 성공했는데, 화면이 안 바뀌어서 한 번 더 누른 경우 (가능성 높음)

- **시나리오**  
  - 1차: 퇴근 버튼 클릭 → 서버에서 정상 저장 → 응답이 느리거나 실패/타임아웃으로 사용자에게 “완료”가 안 보임.  
  - 2차: 같은 사람이 다시 퇴근 버튼 클릭 → 서버는 “이미 오늘 퇴근 있음” → **“บันทึกแล้ววันนี้”** 반환.
- **사용자 관점**: “처음엔 안 된 것 같고, 두 번째엔 ‘이미 저장됐다’고만 나와서, 퇴근 시간이 안 들어간 것 같다”고 느낄 수 있음.
- **관련 코드**  
  - `hr-tab.tsx`: 퇴근 성공 시 `loadButtonState()` + `loadTodayLog()` 호출.  
  - 네트워크 지연/실패 시 알림만 안 뜨거나, 새 상태를 못 불러와서 버튼이 계속 활성화될 수 있음.

→ **쉬는 시간/끝나는 시간과 직접적인 관련은 없고**, “첫 요청은 성공 + UI/네트워크 이슈로 재클릭”으로 설명 가능.

---

### 4-2. 퇴근은 됐는데, “오늘” 기준이 달라서 목록에 안 보이는 경우 (가능성 있음)

- **서버**  
  - `submitAttendance`: “오늘” = **방콕 시간** `new Date().toLocaleDateString('en-CA', { timeZone: 'Asia/Bangkok' })`.  
  - `getTodayAttendanceTypes` / 출퇴근 목록 조회도 방콕 기준으로 “오늘”을 씀.
- **클라이언트**  
  - `hr-tab.tsx`의 `getAttendanceDateRange()`:  
    `today = new Date().toISOString().slice(0, 10)`  
    → **로컬(또는 UTC) 날짜** 사용. 타임존을 지정하지 않음.
- **문제**  
  - 사용자 기기/위치가 방콕이 아니면, “오늘”이 서버와 하루 차이 날 수 있음.  
  - 그 경우 서버에는 “오늘” 퇴근이 저장돼 있는데, 목록/버튼 상태는 “다른 날”로 조회돼서 퇴근한 것처럼 안 보일 수 있음.

→ **쉬는 시간/끝나는 시간**과는 무관하고, **날짜/타임존 불일치** 이슈.

---

### 4-3. store_name 불일치로 “같은 사람인데 두 번 퇴근”이 허용되거나, 반대로 잘못 “이미 있음”으로 나오는 경우 (가능성 있음)

- **submitAttendance (퇴근 중복 체크)**  
  - 조건: `store_name=ilike.{storeName}`  
  - 여기서 `storeName`은 **요청으로 넘어온 값 그대로** (예: `"Ekkamai"`, `"สาขาเอกมัย"`, `"CM Ekkamai"` 등).
- **getTodayAttendanceTypes (버튼 상태/오늘 기록)**  
  - 조건: `store_name=ilike.*{storeName}*`  
  - 즉 **포함 검색**으로, `"Ekkamai"`만 넘겨도 `"CM Ekkamai"` 같은 행이 같이 조회됨.
- **가능한 현상**  
  - 로그인/저장 시 사용하는 매장명과, 중복 체크 시 사용하는 매장명이 조금만 달라도:  
    - “이미 퇴근 있음”으로 나와야 할 상황에서 안 나오거나,  
    - 반대로 다른 매장 기록까지 섞여서 “이미 있다”고 나올 수 있음.  
  - 특히 **같은 지점을 태국어/영문/CM 접두어 등으로 부르는 경우** 영향 가능.

→ **쉬는 시간/끝나는 시간**과는 무관, **매장명 일관성** 이슈.

---

### 4-4. Huamak/Silom “저장했다가 다시 되돌아옴” → 실패 응답 후 화면만 그대로인 경우

- **가능한 원인**  
  - 퇴근 요청이 **실패**한 뒤, 알림만 띄우고 화면 상태를 갱신하지 않아서 “그대로 되돌아온 것처럼” 보이는 경우.  
  - 실패 사례:  
    - **위치/GPS**: 50m 밖, GPS 미등록, 위치 확인 실패 등 → `success: false` + 메시지.  
    - **중복**: 위와 같이 “오늘 이미 [퇴근] 기록이 있습니다” → “บันทึกแล้ววันนี้”.  
  - 클라이언트는 `success: false`일 때 `loadButtonState()` / `loadTodayLog()`를 호출하지 않으므로, 버튼/목록이 이전 상태로 남음.
- **쉬는 시간/끝나는 시간**  
  - 코드 상으로는 퇴근 시 **휴식종료를 먼저 누를 의무**는 없음.  
  - 다만 **스케줄의 plan_out, break_end** 등은 퇴근 시 “조퇴/연장” 계산에만 쓰이고, 퇴근 자체를 막지는 않음.

→ “되돌아옴”은 **실패(위치/중복 등) + 화면 갱신 없음** 조합으로 설명 가능.

---

## 5. 코드상으로 “쉬는 시간 / 끝나는 시간”이 미치는 부분

- **휴식**  
  - `휴식시작` / `휴식종료`는 각각 하루 1회만 허용.  
  - `휴식종료` 시 스케줄의 `break_start`/`break_end`로 “휴게초과/휴게정상”만 계산.  
  - **퇴근 전에 휴식종료를 안 눌러도 퇴근 기록 자체는 가능**하도록 되어 있음.
- **끝나는 시간(plan_out)**  
  - 퇴근 시 **조퇴/연장(overtime)** 계산에만 사용.  
  - **퇴근 기록을 막거나, “이미 기록됨”으로 처리하는 조건은 아님.**

그래서 **“쉬는 시간/끝나는 시간”이 직접 원인이라기보다는**,  
- 첫 퇴근이 이미 성공한 뒤 두 번째 눌러서 “이미 기록됨”이 나오거나,  
- 날짜/매장명/위치 등 다른 조건이 겹쳤을 가능성이 큼.

## 7. 다음에 수정할 때 확인하면 좋은 것

1. **submitAttendance**  
   - 중복 체크 시 사용하는 `store_name` 조건을, `getTodayAttendanceTypes`와 동일하게 **포함 검색(`*storeName*`)** 으로 맞출지 검토.  
   - (반대로 getTodayAttendanceTypes를 정확 일치로 맞출지도 선택.)
2. **클라이언트**  
   - “오늘” 날짜를 **방콕 기준**으로 통일할지 검토 (`getAttendanceDateRange`, 목록 조회 등).  
   - 퇴근 버튼: 요청 중에는 **비활성화**해서 이중 전송 방지.  
   - 퇴근 성공/실패 모두에서 **버튼 상태/목록 새로고침**을 한 번 더 확실히 호출할지 검토.
3. **로그/DB**  
   - 해당 일·해당 직원의 `attendance_logs`에 퇴근(`log_type='퇴근'`)이 실제로 몇 건 있는지, `store_name`/`log_at` 값이 어떻게 들어갔는지 확인하면, 4-1~4-3 중 어떤 케이스인지 구분하는 데 도움이 됨.

이 문서는 **원인 파악용**이며, 위 항목들에 대한 실제 수정은 진행하지 않았습니다.
