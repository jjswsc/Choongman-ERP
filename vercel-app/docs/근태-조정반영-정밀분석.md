# 근태 조정 반영 문제 - 정밀 분석

> **2025-03-04 수정**: form 기반으로 조정값 읽기 변경 및 GET 캐시 비활성화 적용.
> **해결 완료**: form 내 Button에 `type="button"` + `e.preventDefault()` 추가로 form submit 방지. 조정 반영 정상 동작 확인.

## 1. 데이터 흐름 전체 경로

```
[사용자] 조정란에 숫자 입력 → [조정 반영] 클릭
    ↓
[클라이언트] input 값 읽기 → handleApprove(outId, num) 호출
    ↓
[api-client] processAttendanceApproval({ id, optOtMinutes: num })
    ↓
[API] POST /api/processAttendanceApproval
    ↓
[processAttendanceApproval] patch.ot_min = num → supabaseUpdate('attendance_logs', id, patch)
    ↓
[DB] attendance_logs 퇴근 row의 ot_min 컬럼 업데이트
    ↓
[클라이언트] loadRecords() → getAttendanceRecordsAdmin 재조회
    ↓
[getAttendanceRecordsAdmin] attRows에서 r.ot_min 읽음 → rec.otMin 설정 → displayOtMin 반환
    ↓
[UI] 지각/연장 열에 표시
```

## 2. 각 구간별 상세 분석

### 2.1 클라이언트 - input 값 읽기 (의심 지점 1)

**현재 구조:**
- Input: uncontrolled (`defaultValue`), `onChange`/`onBlur`에서 `adjustInputRef.current[String(adjustKey)]`에 저장
- 클릭 시: `adjustInputRef.current[String(adjustKey)] ?? inputEl?.value`

**잠재적 문제:**
1. **adjustKey 불일치**: "조정 반영" 시 adjustKey = row.outLogId. Input의 adjustKey도 동일해야 함.
2. **ref 미갱신**: 사용자가 입력 후 바로 클릭 시, blur가 click보다 먼저 발생하지만 브라우저마다 이벤트 순서 차이 가능.
3. **다중 행**: 여러 행이 있을 때 ref key가 row.outLogId로 구분되므로 이론상 정확함.
4. **초기 미포커스**: 사용자가 한 번도 input을 포커스하지 않고 다른 셀에서 버튼을 클릭하면? → ref 비어있음, inputEl?.value는 defaultValue. 즉 **사용자가 10 입력했어도 다른 셀을 클릭했다가 버튼을 누르면 ref에 저장됨**. input을 직접 클릭해서 10 입력 후 버튼 클릭하면 blur → ref 저장 → click 시 ref 읽음. 정상 동작해야 함.

**추정 원인:** ref/querySelector 실패 시 fromInput이 undefined → defaultVal 사용 → 기존 표시값(예: 158)이 그대로 전송됨. **사용자가 10을 입력했는데 158이 저장되는 시나리오 가능.**

### 2.2 API 전송 (의심 지점 2)

**api-client.ts:**
```js
if (params.optOtMinutes != null) body.optOtMinutes = Number(params.optOtMinutes)
```
- `num`이 0이면 `0 != null` → body에 포함됨. ✅
- `num`이 10이면 포함됨. ✅

**handleApprove:**
```js
optOtMinutes: optOtMinutes != null ? optOtMinutes : undefined
```
- `num`이 undefined면 body에 optOtMinutes 없음 → API에서 patch.ot_min 설정 안 됨.

### 2.3 processAttendanceApproval (의심 지점 3)

- `body?.optOtMinutes != null` 체크: 0도 통과 ✅
- `isClockOut`일 때만 `patch.ot_min` 설정 ✅
- `supabaseUpdate('attendance_logs', id, patch)` 호출

**id 검증:** id = row.outLogId. 이 값은 getAttendanceRecordsAdmin에서 퇴근 로그의 `r.id`로 설정됨. ✅

### 2.4 Supabase 업데이트 (의심 지점 4)

- `supabaseUpdate`: `PATCH /rest/v1/attendance_logs?id=eq.{id}` + body
- `attendance_logs` 테이블에 `ot_min` 컬럼 존재 (schema 확인됨)
- RLS: `Allow all for anon` → 제한 없음

### 2.5 getAttendanceRecordsAdmin - 조회 (의심 지점 5)

- `supabaseSelectFilter`에 `select` 미지정 → `select=*` → ot_min 포함
- 퇴근 처리 시: `rec.otMin = r.ot_min != null && r.ot_min !== '' ? Number(r.ot_min) : null`
- `displayOtMin = otMinForRow != null ? effectiveOtMin : (effectiveOtMin >= 30 ? effectiveOtMin : 0)` ✅

### 2.6 Next.js 캐싱 (의심 지점 6)

- GET /api/getAttendanceRecordsAdmin: 기본적으로 캐싱될 수 있음
- **캐시가 적용되면 업데이트 후에도 이전 응답이 반환될 수 있음**

## 3. 결론 및 권장 조치

1. **input 값 읽기**: HTML `<form>` + `form.elements.namedItem()`로 항상 올바른 값 확보
2. **GET 캐싱**: `getAttendanceRecordsAdmin`에 `cache: 'no-store'` 또는 `dynamic` 설정
3. **디버깅**: processAttendanceApproval 로그로 body.optOtMinutes, patch.ot_min 실제 값 확인
