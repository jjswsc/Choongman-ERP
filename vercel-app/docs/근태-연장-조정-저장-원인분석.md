# 연장 조정 반영이 저장되지 않는 현상 – 원인 분석

코드 수정 없이, **조퇴(저장됨)** 와 **연장(저장 안 됨)** 의 흐름만 비교한 결과입니다.

---

## 1. 처리 흐름 비교

| 단계 | 조퇴 (저장됨) | 연장 (저장 안 됨) |
|------|----------------|-------------------|
| 사용자 | 조정란에 숫자 입력 → "조정 반영" 클릭 | 조정란에 숫자 입력 → "조정 반영" 클릭 |
| 클릭 시 읽는 값 | `fromInput` → ref → state → defaultVal (동일 셀의 input) | **같은 로직** (같은 tr, 같은 input) |
| 호출 | `handleApprove(outId, undefined, undefined, num)` | `handleApprove(outId, num, undefined)` |
| 전달 인자 | 4번째 인자 = `optEarlyMinutes` | 2번째 인자 = `optOtMinutes` |
| API body | `optEarlyMinutes: num` (0이어도 키 존재) | `optOtMinutes: num` (0이어도 키 존재) |
| API에서 파싱 | `'optEarlyMinutes' in body` → 있으면 `Number(body.optEarlyMinutes)` | `body?.optOtMinutes != null` → 있으면 `Number(body.optOtMinutes)` |
| patch 적용 | `patch.early_min = ...` | `patch.ot_min = ...` |
| DB | `attendance_logs.early_min` 업데이트 | `attendance_logs.ot_min` 업데이트 |
| 재조회 | `getAttendanceRecordsAdmin` → `rec.earlyMin = r.early_min` | `getAttendanceRecordsAdmin` → `rec.otMin = r.ot_min` |

흐름상으로는 **연장도 조퇴와 같은 패턴**으로 처리되고, API·DB·재조회 경로에 특별한 차이는 없습니다.

---

## 2. API 쪽 차이 (의심 포인트 1)

**processAttendanceApproval/route.ts**

- **optEarlyMinutes (조퇴)**  
  `(body && 'optEarlyMinutes' in body) ? Number(body.optEarlyMinutes) : undefined`  
  → **키 존재 여부**로 판단. 키만 있으면 0도 적용.

- **optOtMinutes (연장)**  
  `body?.optOtMinutes != null ? Number(body.optOtMinutes) : null`  
  → **값이 null/undefined가 아님**으로 판단. 0이면 그대로 적용.

즉,  
- 조퇴: **키가 body에 있는지**가 중요  
- 연장: **값이 null/undefined가 아닌지**가 중요  

클라이언트에서 `optOtMinutes: num`(숫자)을 보내면 서버는 `!= null`로 받을 수 있어야 합니다.  
다만, **실제 요청 body에 `optOtMinutes`가 빠지거나, null/undefined로 들어오는 경우**가 있으면 연장만 적용이 안 됩니다.

---

## 3. 클라이언트에서 값이 잘못 넘어가는 경우 (의심 포인트 2)

조정 반영 클릭 시:

- `outId` = `row.outLogId` (퇴근 로그 id)
- 같은 행의 input을 `tr.querySelector("input[data-adjust-key]")` 로 찾음
- `otVal` = fromInput → ref → state → defaultVal 순으로 결정
- `num = parseInt(otVal, 10)` 후 0 이상이면 그대로, 아니면 0

**연장일 때만 문제가 된다면:**

- **연장 행에서만** `fromInput` / ref / state가 비어 있거나,  
- **연장 행에서만** `defaultVal`(예: `row.otMin ?? row.diffMin`)이 들어가서  
  **사용자가 입력한 값이 아니라 기존 지각/연장 숫자가 그대로 num으로 넘어갈 가능성**이 있습니다.

즉, “저장이 안 된다”가  
- **서버까지는 제대로 가는데 DB에 반영이 안 되는 것**인지,  
- **서버로 가는 값 자체가 이미 예전 값(지각/연장 열 값)인지**를 나눠야 합니다.

---

## 4. DB/스키마 가능성 (의심 포인트 3)

- `supabaseUpdate('attendance_logs', id, patch)` 로 `patch` 객체를 그대로 PATCH 요청.
- `patch`에 `ot_min`이 들어 있으면, Supabase는 해당 컬럼을 업데이트합니다.
- **만약 `attendance_logs` 테이블에 `ot_min` 컬럼이 없거나**,  
  타입/제약 때문에 무시되거나 에러가 나면,  
  조퇴(`early_min`)만 반영되고 연장(`ot_min`)만 반영이 안 될 수 있습니다.

(현재 프로젝트에는 `attendance_logs` 스키마 정의 파일이 없어, DB에 실제로 `ot_min` 컬럼이 있는지는 코드만으로는 확인 불가.)

---

## 5. 확인하면 좋은 것들 (원인 특정용)

1. **실제로 서버에 무엇이 도착하는지**  
   - 브라우저 개발자 도구 → Network → "조정 반영" 클릭 시 `processAttendanceApproval` 요청 선택  
   - Request payload에 **`optOtMinutes`** 가 있고, 값이 **입력한 숫자**인지 확인.

2. **연장일 때만 payload가 다른지**  
   - 같은 방식으로 **조퇴** 한 건과 **연장** 한 건을 각각 눌러서  
     body에 `optEarlyMinutes` / `optOtMinutes` 가 각각 어떻게 나오는지 비교.

3. **DB에 실제로 반영되는지**  
   - Supabase 대시보드 등에서 `attendance_logs` 의 해당 행(id = 퇴근 로그 id)을  
     조정 반영 전/후로 비교해서 `ot_min` 이 바뀌는지 확인.

4. **서버 로그**  
   - `processAttendanceApproval` 안에  
     `body.optOtMinutes`, `patch.ot_min`, `id` 를 잠깐 로그로 찍어보면  
     “클라이언트가 보낸 값”과 “실제로 patch에 들어간 값”을 구분할 수 있습니다.

---

## 6. 정리

- **코드 경로만 보면** 조퇴와 연장은 **같은 방식**으로 처리되도록 되어 있고,  
  API·supabaseUpdate·getAttendanceRecordsAdmin 모두 연장(ot_min)을 다루고 있습니다.
- 따라서 “연장만 안 된다”면 아래 중 하나일 가능성이 큽니다.
  1. **클라이언트**: 연장 행에서만 조정란 값이 읽히지 않아, 예전 값(지각/연장 열 숫자)이 `optOtMinutes`로 전달되고 있음.
  2. **API**: 요청 body에 `optOtMinutes`가 없거나 null/undefined로 들어와서 `patch.ot_min`이 세팅되지 않음.
  3. **DB**: `attendance_logs`에 `ot_min` 컬럼이 없거나, 제약/트리거 등으로 업데이트가 무시되거나 실패함.

**다음 단계 권장:**  
위 5번의 1~3(Network payload, DB 값, 필요 시 서버 로그)을 한 번씩 확인해 보시면,  
“입력값이 서버까지 가는지” / “DB에는 쓰이는지”가 나뉘어서 **원인이 클라이언트인지, API인지, DB인지** 좁혀집니다.

---

## 7. 진행 상황 (스키마 제외)

- **스키마**: `ot_min`/`early_min` 추가 마이그레이션 적용해 봤으나 동일 → **스키마는 원인 아님**.
- **API 임시 로그**: `processAttendanceApproval` 에서 `decision === '승인완료'` 이고 body에 `optOtMinutes` 또는 `optEarlyMinutes` 가 있을 때  
  `[processAttendanceApproval] { id, bodyOptOt, bodyOptEarly, patchOt, patchEarly }` 를 서버 로그에 출력하도록 추가함.
- **확인 방법**: 연장 행에서 조정 입력 후 "조정 반영" 클릭 → 서버 로그에서  
  - `bodyOptOt` 가 **입력한 숫자**로 나오는지  
  - `patchOt` 가 설정되어 있는지  
  확인. `bodyOptOt` 가 없거나 다르면 **클라이언트**, `patchOt` 있으면 **API·DB** 쪽 추가 확인.
