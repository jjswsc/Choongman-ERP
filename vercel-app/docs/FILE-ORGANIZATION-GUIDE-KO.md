# 파일 정리 가이드 (영향 없는 정리용)

이 문서는 **프로그램 동작을 바꾸지 않고** 파일을 보기 좋게 유지하기 위한 기준입니다.
기능 추가/버그 수정 시, 신규 파일부터 아래 규칙을 적용합니다.

## 1) 핵심 원칙

- 기능(도메인) 기준으로 먼저 찾고, 그 다음 파일 타입을 찾습니다.
- 기존 import 경로를 깨뜨리는 대규모 이동은 한 번에 하지 않습니다.
- 신규 파일은 규칙에 맞춰 추가하고, 기존 큰 파일은 수정 타이밍에 점진 분리합니다.

## 2) 폴더별 역할

- `app/`: 라우트 엔트리, 페이지, 레이아웃
- `app/api/`: HTTP 엔드포인트(`route.ts`)
- `components/`: 화면/위젯 UI 컴포넌트
- `lib/`: 비즈니스 로직, 데이터 접근, 공통 유틸
- `sql/`: 스키마/마이그레이션/RPC/정책 스크립트
- `docs/`: 운영/아키텍처/가이드 문서

SQL 파일 찾기는 [`SQL-INDEX.md`](./SQL-INDEX.md)를 우선 참고합니다.

## 3) 신규 파일 배치 규칙

- API 핸들러: `app/api/<도메인>/<행위>/route.ts`
- 화면 로직:
  - 페이지 엔트리: `app/.../page.tsx`
  - 재사용 UI: `components/<도메인>/...`
  - 로직/검증/매퍼: `lib/<도메인>/...` 또는 기존 `lib/*` 관례 유지
- SQL:
  - 신규 스키마/컬럼 변경: `sql/<기능명>.sql`
  - 대형 일괄 스크립트는 `*_all_in_one.sql` 패턴을 유지하되, 원본 변경 스크립트를 별도로 남깁니다.

## 4) 대형 파일 점진 분리 기준

- `page.tsx` 또는 `route.ts`가 300~500줄 이상 커지면 분리를 고려합니다.
- 분리 우선순위:
  1. UI 섹션 (`components/...`)
  2. 데이터 조회/저장 (`lib/...`)
  3. 입력 검증/매핑 (`lib/...`)
- 분리 시 함수/컴포넌트 이름은 기존 의미를 유지해 검색성을 보존합니다.

## 5) 네이밍 규칙 (권장)

- 파일: `kebab-case`
- React 컴포넌트: `PascalCase`
- 내부 유틸 함수: `camelCase`
- SQL 파일: 기능이 드러나는 명사형 이름 (`items_account_subject_id.sql` 같은 형태)

## 6) 안전한 정리 체크리스트

- 동작 변경 없음 (UI/비즈니스 로직 불변)
- import 경로 변경 시 타입체크/빌드 확인
- API 경로 문자열 변경 금지 (클라이언트 영향 큼)
- SQL 파일 이동/이름 변경 시 배포 스크립트 참조 여부 확인

## 7) 권장 작업 방식

- 큰 이동 대신 "신규 파일부터 규칙 적용" 방식으로 진행
- 한 PR/커밋에는 하나의 정리 주제만 포함
- 리팩터링 전후 동작 비교가 쉬운 단위로 잘라서 수행
